# 架构说明

## 它到底是什么

不是一个"模型适配器"，而是**一个跑在 DSH 进程内的 HTTP 代理**，
对外提供 OpenAI 兼容接口，对内管理一堆上游渠道。

```
                      ┌──────────────────────────────────────────┐
   DSH agent loop ──► │  free-pool 路由 (http://127.0.0.1:8787/v1)│
   （或任何程序）      │                                          │
                      │  1. 读请求体，推断需要什么能力            │
                      │  2. 按能力硬过滤候选渠道                  │
                      │  3. 跳过 manualOnly / 冷却中的            │
                      │  4. 按 priority 排序，逐个尝试            │
                      │  5. 失败分类 → 分级冷却 → 换下一个         │
                      └───────────────┬──────────────────────────┘
                                      │
        ┌──────────┬──────────┬───────┴───────┬──────────┬──────────┐
        ▼          ▼          ▼               ▼          ▼          ▼
      千帆       百炼       智谱          硅基流动   OpenRouter   火山（手动）
    6 token   14 token   177~465 思考   174 token   42 token      付费
```

## 模块职责

| 文件 | 职责 |
|---|---|
| `lib/paths.mjs` | 数据目录解析（`~/.dsh/llm-router/`），首次运行生成配置模板 |
| `lib/config.mjs` | 读 `config.json` + `.env`，规范化 provider；解析 `auto` / `auto:vision` / `id::model` |
| `lib/health.mjs` | 每个渠道的健康状态、冷却退避、失败分类、**恢复时间解析** |
| `lib/pool.mjs` | 候选选择：能力过滤 → manualOnly 过滤 → 优先级排序 → 冷却跳过 |
| `lib/server.mjs` | HTTP 服务器与 fallback 主循环、SSE 透传 |
| `lib/probe.mjs` | 独立进程直连上游做自检，跑完把结果回报给代理 |
| `lib/discover.mjs` | 从 OpenRouter 拉零价模型清单，对比并可选写回配置 |
| `lib/balance.mjs` | 查余额（目前只有 OpenRouter 有公开接口） |
| `lib/cli.mjs` | 不依赖 DSH 的独立启动入口（测试也用这个） |
| `dist/index.js` | Host 插件：启动内嵌代理 + 注册路由 + 读 catalog |
| `dist/client.js` | client 插件：注册「设置 → 渠道池」分区（iframe 嵌面板） |
| `dist/panel.html` | 面板本体（自包含 HTML/CSS/JS） |

## 关键设计决策（这些都是踩过坑才定下来的）

### 1. 为什么只有在「还没写给客户端任何字节」之前失败才允许换渠道

流式请求一旦开始向客户端输出，就无法"重放"—— 客户端会收到半截响应再重来。
所以流式路径**先等上游第一个 chunk 落地**，确认成功后才写客户端响应头。
这样 429 / 5xx / 空流 都能被安全接管，而不是把半截内容吐出去。

### 2. 为什么探测失败不设冷却（`markProbe` 与 `markFailure` 分开）

探测是**独立进程直连上游**做的，为的是不受代理的能力过滤干扰 ——
只有这样才能真正验证 `capabilities` 声明准不准。
它不是真实流量，所以只更新统计、**不触发冷却**。否则一次误报的探测会把好渠道冷却掉。

但探测结果要回报给代理（`POST /admin/report`），否则面板上会一直显示「未测试」——
这是最初的一个设计断裂，后来补上的。

### 3. 为什么能力过滤是硬规则，不是偏好

往纯文本渠道发图片，实测有些上游（火山 / 通义）会返回 **HTTP 200 然后开始瞎编**。
这比直接报错危险得多 —— 你会拿到一个"看起来正常"的错误答案。
所以 `capabilities` 里没声明 `image` 的渠道，带图请求**根本不会被路由过去**。

### 4. 为什么失败要分类（429 / 5xx / 401 / 模型名错）

| 失败类型 | 含义 | 处理 |
|---|---|---|
| 429 | 限流，额度窗口型 | 退避 60s（听 `Retry-After`），到点立刻放回 |
| 5xx / 网络 / 空流 | 瞬时抖动 | 退避 20s |
| 401 / 402 / 403 | 密钥失效或余额耗尽 | 退避 30min（别让它每个请求都白等一轮超时） |
| 400 / 404 | 模型名不对，是配置问题 | 退避 5s，**不指数放大** |

一律当"失败"处理的话，一把填错的 key 会在每个请求上浪费一轮超时。

### 5. 为什么优先级是「实测」出来的，不是拍脑袋填的

同样回答两个字，不同渠道的开销差 **27 倍**（14 token vs 386 token）——
差别在于有些模型是思考型的，会把预算烧在 `reasoning_content` 上。

所以「探测并优化优先级」会拿真实的 `total_tokens` 排序并写回配置。
排序依据是数据，不是直觉。

### 6. 为什么 client 侧用 iframe 而不是重写 React

面板本体是 Host 渲染的一份自包含 HTML。client 侧只注册一个 `settings.section`，
里面挂 iframe 指向 `/llm-router`。好处：

- 管理界面只有**一份实现**
- 不绑定 DSH 前端的内部组件结构（那些是私有的，一变就坏）
- iframe 与宿主同源同端口，没有跨域问题

代价是它不在设置侧边栏的"原生"位置，而是一个独立页面 —— 但这个取舍值得。

## 数据流：一次请求

```
1. POST /v1/chat/completions  { model: "auto", messages: [...带图...] }
2. inferNeeds()          → needs = { image }
3. selectCandidates()    → 过滤掉没有 image 能力的渠道；跳过 manualOnly；跳过冷却中的
                         → 按 priority 排序
4. callUpstream()        → 逐个尝试（同一渠道内多把 key 也轮换）
5. 失败 → classifyStatus() → markFailure() 设冷却 → 换下一个
6. 成功 → 透传响应；非流式顺手提取 usage 计入统计
```

## 已知的取舍

- **代理随 DSH 启停**：跑在 DSH 进程内。DSH 关了代理就没了。
  （需要 7×24 的话用 `lib/cli.mjs` 独立跑，插件检测到端口被占会自动复用）
- **余额查不到**：大多数平台没有公开接口，只能显示"什么时候恢复"（从限流错误解析）
- **不为对抗风控做任何优化**：见 SECURITY.md 的"安全边界"
